What is ICP-Brasil signing,
and how do you do it right?

Last updated: 2026-06-30

ICP-Brasil is Brazil's national PKI: a signature made with an e-CPF or e-CNPJ certificate carries the same legal weight as ink on paper. Getting a PDF to pass the government validator takes more than a valid signature, and the private key usually lives in a token or HSM that must never hand the key out. This guide explains the profiles, the rules, and how to sign without ever exposing the key.

A signature with the weight of a handwritten one

ICP-Brasil (Infraestrutura de Chaves Publicas Brasileira) is the public-key infrastructure operated by Brazil's ITI. Under it, accredited authorities issue certificates such as the e-CPF for people and the e-CNPJ for companies. Because the law (MP 2.200-2 of 2001) recognizes these signatures as legally equivalent to a handwritten one, they are used for invoices, contracts, notarial acts, court filings and anything that must hold up as evidence.

The catch is that "valid signature" is not the same as "accepted by the government validator". A file is only an ICP-Brasil signature if it follows the official standard, DOC-ICP-15, whose profile for PDF is PAdES. Miss one of its rules and ITI's validator will mark the document as indeterminate or reject the chain, even though the math is perfect.

The profiles: AD-RB, AD-RT, AD-RC, AD-RA

ICP-Brasil defines a ladder of signature profiles, each one adding a guarantee on top of the last. They line up directly with the PAdES baseline levels.

AD-RB Basic reference

A signature plus a reference to a signature policy, with no timestamp. The baseline, and what most documents need. Maps to PAdES-B-B.

AD-RT Time reference

Adds a trusted timestamp from an accredited time-stamping authority, proving when the signature was made. Maps to PAdES-B-T.

AD-RC Complete references

Adds references to the validation data (the certificate chain and revocation status) so the signature can be checked later.

AD-RA Archival references

Embeds the validation data and an archival timestamp for long-term validation, so the signature survives the certificate's expiry. Maps to PAdES-B-LTA.

For PAdES the policy lives in its own OID arc, 2.16.76.1.7.1.11.x, separate from the CAdES arc 2.16.76.1.7.1.1.x. Reference the CAdES policy in a PDF and the validator will not recognize it.

The key never leaves your HSM or token

ICP-Brasil private keys are meant to be non-exportable: an A3 token, a smartcard, or a cloud HSM such as Azure Key Vault, VIDaaS or BirdID. A signing library that asks you to hand over the key is a non-starter. rust-pdf uses deferred signing instead: it does the PDF work, hands you the bytes to be signed, and embeds the signature you get back. The key stays where it belongs.

  • Signer callback: the library builds the signed attributes and calls your code for the raw RSA signature, then assembles the CMS.
  • Two-phase prepare and complete: phase one returns the hash to sign, you send it to the HSM across an async boundary, phase two embeds the container.
  • You supply the certificate chain separately from the key, exactly as a cloud cert plus intermediates.
  • RSA with SHA-256, the algorithm e-CPF and e-CNPJ A1 and A3 certificates use, with a configurable reserved size for variable HSM containers.

What makes a signature pass ITI's VALIDAR

ITI's Verificador de Conformidade checks more than the cryptography. Three things decide whether a PAdES signature is accepted as ICP-Brasil conformant.

DocMDP

The first signature must carry the modification-detection transform (P=2, V=1.2). Without it the validator reports the result as indeterminate.

The PAdES policy

The signature-policy identifier must use the PAdES policy OID and the matching artifact hash, not the CAdES policy. This is the most common mistake.

The full chain

The signer certificate plus every intermediate authority up to the ICP-Brasil root must be embedded, so the validator can build trust.

A signature produced with rust-pdf, using a real e-CNPJ whose key stayed in the macOS keychain, was approved by ITI's VALIDAR, and confirmed independently by pdfsig and openssl.

How to sign for ICP-Brasil with rust-pdf

You provide the certificate and a callback that returns the raw RSA signature from your HSM or token. rust-pdf builds a PAdES signature with DocMDP, the AD-RB policy and your chain. The policy values below are the official ICP-Brasil PAdES AD-RB v1.3 artifact. 

# pip install rustpdf
import rustpdf

# Your HSM/token signs the bytes. The private key never enters the library.
def hsm_sign(data: bytes) -> bytes:
    return my_hsm.sign_rsa_sha256(data)        # Azure Key Vault, VIDaaS, A3 token...

policy = rustpdf.SignaturePolicy(
    oid="2.16.76.1.7.1.11.1.3",                # ICP-Brasil PAdES AD-RB v1.3
    hash=bytes.fromhex("23e4be4b9b362172e4ebb0e72b86a133ece5aad843d8651c6e38a0ba3f08fc60"),
    uri="http://politicas.icpbrasil.gov.br/PA_PAdES_AD_RB_v1_3.der",
)
opts = rustpdf.SigningOptions(
    pades=True,
    certify=rustpdf.Certify.FORMS,             # DocMDP P=2
    policy=policy,
)
signed = rustpdf.sign_with(pdf, cert_der, hsm_sign, chain=chain, options=opts)

ICP-Brasil signing FAQ

What is ICP-Brasil?

ICP-Brasil (Infraestrutura de Chaves Publicas Brasileira) is Brazil's national public-key infrastructure, run by the ITI. Certificates issued under it, such as the e-CPF for individuals and the e-CNPJ for companies, give a digital signature the same legal weight as a handwritten one under Brazilian law (MP 2.200-2 of 2001). Signatures must follow the official document standard DOC-ICP-15, whose PDF profile is PAdES.

What are the AD-RB, AD-RT, AD-RC and AD-RA profiles?

They are ICP-Brasil's signature profiles, each one stricter than the last. AD-RB (Referencia Basica) is the baseline: a signature plus a reference to a signature policy, with no timestamp, mapping to PAdES-B-B. AD-RT adds a trusted timestamp (PAdES-B-T). AD-RC adds complete validation-data references, and AD-RA adds embedded validation data and an archival timestamp for long-term validation (PAdES-B-LTA). For PAdES the policy lives in its own OID arc, 2.16.76.1.7.1.11.x, separate from the CAdES arc.

Can I sign with an HSM or A3 token without exposing the private key?

Yes. ICP-Brasil keys often live in a cloud HSM (Azure Key Vault, VIDaaS, BirdID) or an A3 token or smartcard, where the private key is non-exportable by design. rust-pdf uses deferred signing: it prepares the PDF, computes the bytes to be signed, and asks your code or HSM for the raw RSA signature, then assembles and embeds the CMS. The key never reaches the library. There is a synchronous signer callback and a two-phase prepare-and-complete flow for asynchronous HSM calls.

How do I make a signature pass ITI's VALIDAR?

Three things matter beyond a cryptographically valid signature. First, the first signature must carry a DocMDP transform, or VALIDAR reports the result as indeterminate. Second, the signature-policy identifier must use the PAdES policy OID (2.16.76.1.7.1.11.1.x with the matching artifact hash), not the CAdES one. Third, the full certificate chain up to the ICP-Brasil root must be embedded. rust-pdf does all three, and a signature produced this way with a real e-CNPJ was approved by VALIDAR.

Does rust-pdf support PAdES for ICP-Brasil?

Yes. rust-pdf produces PAdES (ETSI.CAdES.detached) signatures with the ESS signing-certificate-v2 attribute, an explicit signature policy, DocMDP certification, an embedded certificate chain, and deferred (HSM) signing so the key never leaves your control. The same API is available in Python, C#, Go, Node, PHP, Ruby, Java, Swift and Delphi.
